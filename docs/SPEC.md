# Master Product Specification — Offline Cricket Score Counter & Tournament Manager

> Source of truth supplied by the product owner. Section numbers (§N) are referenced throughout the design docs and code comments. Do not edit this file to "match" the implementation — change the implementation.

## ROLE

Act as a senior product architect, cricket scoring-domain expert, UX/UI designer, React Native engineer, database architect, QA engineer, and technical product manager, designing a production-quality mobile application: **Offline Cricket Score Counter & Tournament Manager**.

The application must be offline-first, zero-cost, highly reliable, fast to operate during live cricket matches, and flexible enough to manage complete cricket tournaments. Do not treat this as a simple CRUD application; treat it as a real sports scoring and tournament-management product.

- **MODE 1 — SINGLE MATCH:** a user creates and scores one cricket match.
- **MODE 2 — TOURNAMENT:** a user creates a tournament containing multiple teams, stages, pools/groups, fixtures, matches, standings, qualification rules, knockout stages, semifinals, finals, statistics, and manual organizer overrides.

Both modes must use the **same underlying match/scoring engine**.

---

## §1 Product vision

A digital cricket scorebook that feels professional, fast, trustworthy, modern, sport-focused, human-designed, easy to understand, extremely reliable, attractive without being flashy.

Must NOT look AI-generated. Avoid: excessive glassmorphism, huge gradients, neon colors, excessive rounded cards, unnecessary floating elements, excessive shadows, fake statistics, decorative dashboards, giant icons, excessive animations, cyberpunk styling, cryptocurrency-style layouts, generic SaaS dashboards, random cards everywhere.

Design language: **Modern Cricket Scorebook** — the familiarity of a traditional cricket scorebook with the precision of modern sports technology; something a professional scorer, school organizer, university sports department, club, or casual cricket group would genuinely use.

## §2 Core product principles

1. **Speed** — record a normal ball with essentially one tap.
2. **Accuracy** — all scores and statistics come from a reliable scoring engine, not duplicated calculations in different screens.
3. **Recovery** — an interrupted device must not destroy a match.
4. **Flexibility** — tournaments do not always follow one standard format; the organizer can customize the competition.
5. **Automatic + Manual Control** — calculate as much as possible automatically while allowing organizers to override appropriate decisions.
6. **Offline First** — core functionality works with no network connection.
7. **Human-Centered UI** — every element must exist for a reason.

## §3 Zero-cost technology requirements

Free/open-source only. Stack: React Native + Expo, TypeScript, Expo Router, expo-sqlite, Zustand, lucide-react-native, react-native-gifted-charts, SQLite/AsyncStorage where appropriate, expo-print (PDF), expo-sharing, Jest + React Native Testing Library, Maestro or Detox (E2E), Git + GitHub.

Do not require: Firebase, Supabase, MongoDB Atlas, PostgreSQL server, paid API, cloud backend, authentication server, paid analytics, paid infrastructure. Fully usable with **no internet connection**.

## §4 SDLC

1. Planning — scope, target users, MVP, future features, technical constraints, risks, success criteria.
2. Requirements — functional/non-functional requirements, user stories, business rules, cricket scoring rules, tournament rules, edge cases.
3. System design — architecture, database ERD, state model, domain model, component architecture, design system, navigation structure.
4. UI/UX design — information architecture, user journeys, wireframes, light mode, dark mode, responsive behavior, interaction states.
5. Development — module by module.
6. Testing — Unit: scoring calculations, rules engine, NRR, qualification, standings. Integration: match lifecycle, tournament lifecycle, SQLite persistence. E2E: create tournament, create match, score match, complete match, update standings, qualify teams, finish tournament.
7. Deployment preparation — performance, offline behavior, database reliability, accessibility, export, device compatibility.

## §5 Product modes

Home screen clearly offers: **+ NEW MATCH**, **TOURNAMENTS**, **Continue Match**, **Recent Matches**.
Main areas: **Match** (create and score an individual match), **Tournament** (create and manage a competition), **History** (previous matches and tournaments), **Settings** (theme, scoring preferences, feedback, data, application options).

## §6 Match management

Complete ball-by-ball scoring. Match setup: match title, Team A, Team B, venue, date, time, match format, number of overs, players, toss winner, toss decision, maximum overs per bowler, wide rules, no-ball rules, powerplay rules, optional custom rules.

## §7 Number of overs

Never permanently fixed. Choices: 1, 2, 5, 6, 10, 20, 25, 30, 40, 50, or a custom typed number (e.g. 17). The scoring engine adapts automatically. The organizer can modify planned overs where appropriate (e.g. 20 overs → rain delay → 12 overs). Do not assume traditional T10/T20/ODI formats.

## §8 Match formats

Presets T5, T10, T20, T30, T40, T50, Custom. Presets only preconfigure rules and remain editable.

## §9 Live scoring

The single most important screen. Optimized for one-handed use, thumb accessibility, outdoor sunlight, fast repeated input, minimal eye movement. Primary buttons: `0 1 2 3 4 6 EXTRAS WICKET`. Normal deliveries never require navigating multiple screens.

## §10 Live score header

Team name; score `142 / 4`; `16.4 OVERS`; `CRR 8.52`; `RRR 9.12`; plus target, runs required, balls remaining where applicable. Score is visually dominant.

## §11 Batsman area

`Ali 42* (24)` / `Ahmed 31 (27)`. Clearly identify the striker with an icon/marker/subtle indicator, not only an asterisk. Provide **Swap Strike** for manual correction.

## §12 Bowler area

`Hassan 3.4 - 0 - 28 - 2  ECO 7.00`. Track overs, maidens, runs, wickets, economy, dot balls, legal deliveries.

## §13 Current over

Compact sequence `1 4 0 W WD 2`; each event distinguishable but restrained visual states.

## §14 Ball event model

Every delivery is an event:

```
BallEvent { inningsId, overNumber, ballNumber, batsmanId, nonStrikerId, bowlerId, batterRuns, extraRuns,
            totalRuns, extraType, wicketType, dismissedPlayer, fielder, isLegalDelivery, timestamp }
```

Do NOT store only the final score. Preserve delivery history — essential for undo, redo, statistics, recovery, scorecards, analytics, NRR, historical correction.

## §15 Undo / Redo

Unlimited undo where practical. Undo must correctly reverse runs, extras, wickets, strike changes, batter replacements, bowler state, over state. Redo optionally shown after undo. Never implement undo as `score = score - 1`; reverse the scoring event and recalculate state.

## §16 Manual ball edit

Correct historical mistakes (e.g. 17.3 recorded FOUR → edit to 0/1/2/3/4/6/Wide/No Ball/Wicket). When editing: 1) validate, 2) recalculate dependent data, 3) score, 4) batting, 5) bowling, 6) partnerships, 7) tournament standings if relevant, 8) NRR if relevant. Warn the organizer when a historical change affects tournament calculations.

## §17 Extras

- Wide: 1, 2, 3, 4, 5, custom
- No ball: NB+0, +1, +2, +3, +4, +6, custom
- Bye: 1, 2, 3, 4, custom
- Leg bye: 1, 2, 3, 4, custom

Separate **batsman runs** from **extra runs**.

## §18 Wicket system

Bowled, Caught, LBW, Run Out, Stumped, Hit Wicket, Retired Hurt, Retired Out, Obstructing the Field. Additional fields: fielder, dismissed batsman, incoming batsman. The wicket flow must remain fast.

## §19 Strike management

Automatically: odd-run rotation, end-of-over rotation, wicket replacements, strike changes. Always allow **Manual Swap Strike**.

## §20 Free hit / no-ball / powerplay

Rules engine supports free hit, powerplay, custom powerplay overs, custom no-ball penalty, custom wide penalty. Not hard-coded into UI components.

## §21 Super over

Optional, configurable. Stored as a related stage rather than corrupting the original innings.

## §22 Match result states

Scheduled, Live, Paused, Completed, Postponed, Cancelled, Abandoned, No Result, Tied, Walkover. Never assume every match ends with Team A or Team B winning.

## §23 Match recovery

After every scoring event: user taps → validate event → update scoring state → persist event → update derived statistics → refresh UI. If the phone crashes, loses battery, closes the app, or restarts, the user can resume. On startup show: `MATCH IN PROGRESS / Pakistan XI 142/4 16.4 overs / [RESUME] [SAVE & EXIT] [DISCARD]`.

## §24 Tournament module

Multiple teams, pools/groups, uneven pools, random assignment, manual assignment, team transfer, team replacement, team swapping, single round robin, double round robin, custom fixture generation, manual fixture creation, standings, points, NRR, tie breakers, qualification, knockout, quarterfinal, semifinal, final, manual override.

## §25 Tournament creation flow

Create Tournament → Tournament Information → Add Teams → Choose Stage Structure → Configure Rules → Create Pools/Groups → Generate Fixtures → Review → Confirm Tournament.

## §26 Tournament information

Name, season, description, logo, organizer, start date, end date, venue(s). Optional: location, contact details, notes.

## §27 Team management

Arbitrary practical number of teams; architecture supports **at least 128 teams** without hard-coding the UI to a small number. Team: name, short name, logo, captain, players, optional seed.

## §28 Tournament structure

League (one table), Pools/Groups, Knockout, League + Knockout (Group → QF → SF → Final), Custom (organizer builds own stages).

## §29 Stage builder

Flexible Tournament Stage Builder (e.g. Group Stage → Super 8 → Semifinals → Final). Each stage defines: name, type, teams entering, pools, number of matches, points system, tie breaker, qualification rule, fixture generation method.

## §30 Pool/group system

Automatic random assignment (16 teams → shuffle → Pools A–D), manual assignment, seeded assignment (future-compatible).

## §31 Randomization

Normal random and seeded random (optional seed, e.g. 847291). Never silently replace existing arrangements — warn "Current pool arrangement will be replaced." Allow undo.

## §32 Uneven pools

Do not force equal pools (10 teams → 4/3/3 allowed). Warn: "Teams in different pools may play different numbers of matches." Organizer chooses how qualification handles this.

## §33 Team transfer

Move (Team X Pool A → Pool C), Replace (Pool A Team X → Team Y), Swap (Pool A Team X ↔ Pool B Team Y).

## §34 Pool edit impact

Before applying a change after fixtures exist, show POOL CHANGE IMPACT: affected fixtures count, pool standings, qualification, NRR — [Cancel] [Continue]. Never silently invalidate tournament data.

## §35 Fixture generator

Single round robin, double round robin, custom number of encounters per opponent.

## §36 Fixture review

Generation is never irreversible: Generate → Preview → Organizer edits → Confirm.

## §37 Manual fixture creation

`+ Add Match` with stage, pool, Team A, Team B, date, time, venue, match format, overs, notes.

## §38 Fixture editing

Edit teams, date, time, venue, stage, pool, status, match format, overs. Completed matches: edits restricted and audited.

## §39 Postponed/cancelled

Scheduled → Postponed → Rescheduled → Completed; Scheduled → Cancelled; Live → Abandoned.

## §40 Points system

Not hard-coded. Configurable Win/Tie/No Result/Loss (e.g. 2/1/1/0 or 3/1/1/0).

## §41 Net Run Rate

Calculated automatically from delivery/innings data: average runs scored per over − average runs conceded per over. Must account for all-out innings, completed chases, reduced-over matches, no result, abandoned matches, walkovers, custom competition rules. No duplicated NRR calculations — a dedicated **Tournament Statistics Engine**.

## §42 Standings engine

Auto-updates after a match completes. Per team: played, wins, losses, ties, no result, points, runs scored, runs conceded, overs faced, overs bowled, run rate, NRR.

## §43 Tie-breaker engine

Configurable order, e.g. Points → NRR → Head-to-Head → Most Wins → Organizer Decision; or Points → Head-to-Head → NRR.

## §44 Qualification rule builder

Never hard-code "top 2 qualify". Examples: top 2 from each pool; pool winners + best 4 runners-up; top 8 overall; organizer manually selects qualifiers.

## §45 Qualification slots

Stage slots, e.g. SEMIFINAL Slot 1 → Pool A Winner, Slot 2 → Pool B Runner-up, Slot 3 → Pool C Winner, Slot 4 → Best Runner-up. Later stages link to dynamic results.

## §46 Knockout system

Quarterfinal, semifinal, final, custom knockout. Seeding: Fixed (A1 v B2, B1 v A2), Random draw, Ranking-based (1v8, 2v7, …).

## §47 Manual qualification override

Organizer may qualify a team, eliminate a team, reassign a team to a stage. Every override clearly marked **Manual Override** and recorded in the audit log.

## §48 What-if simulation (advanced)

"What if Team A wins the next match?" — Current table → hypothetical result → simulated table → qualification consequences. Never modifies the real tournament.

## §49 Tournament dashboard

Not a collection of giant cards. Prioritize: tournament name; teams/pools/format; current stage; matches progress (24/48); next match; standings. Typography, spacing, separators, compact surfaces. No card per statistic.

## §50 Standings view

Pool tabs, overall standings where applicable, points, NRR, qualification indicator, matches remaining. Columns Pos, Team, P, W, L, NR, Pts, NRR. Ranking generated from configured rules.

## §51 Qualification status

Qualified / In contention / Eliminated — not color-only; explanatory text ("Team A has mathematically qualified for the semifinal." / "Team B is still in contention.").

## §52 Tournament statistics

Team: matches, wins, losses, points, NRR, runs scored, runs conceded. Player: runs, average, strike rate, fours, sixes, wickets, economy, best score, best bowling. Tournament: total matches, total runs, total wickets, highest score, most sixes, most fours, best bowling, highest partnership. All computed locally.

## §53 Tournament audit log

History of important changes (team moved pools, fixture rescheduled, result corrected). Record what changed, previous value, new value, date/time, reason where supplied.

## §54 Automatic vs manual control

Throughout the app: Pool assignment (Random/Manual), Fixtures (Automatic/Manual), Qualification (Automatic/Manual Override), Standings (Automatic + Manual Override). Calculate by default; never pretend there is only one valid format.

## §55 Structural editing rules

Before tournament begins: broad changes allowed. After matches begin: warn before changes affecting pools, fixtures, standings, qualification, NRR. After completed matches: explicit confirmation for historical changes. Never silently delete or alter completed match data.

## §56 Tournament templates

Save reusable structures (e.g. 8-Team T20: 2 pools × 4, round robin, top 2 qualify, semifinal, final). Future: 4-team league, 8-team knockout, 16-team group, 20-team pools, custom club format.

## §57 Database / ERD

Relational SQLite: TOURNAMENTS → TOURNAMENT_STAGES → (POOLS → POOL_TEAMS, FIXTURES, QUALIFICATION_RULES); TOURNAMENTS → TEAMS → PLAYERS; TOURNAMENTS → MATCHES → INNINGS → BALLS. Also standings, rules, venues, partnerships, events, audit logs.

## §59 Database principles

Foreign keys, transactions, indexes, migrations, constraints, validation. Derived statistics are never the only source of truth. **Delivery history is the authoritative source for match scoring.**

## §106 Liquid Glass amendment (product owner decision, 2026-10-01)

The product owner requires a **liquid glass** material in the UI. This amends §1, §67–§71 and §101: glass is now part of the identity. "Excessive glassmorphism" in §1 still means glass applied indiscriminately — glass belongs to the **floating control and navigation layer**, while scorebook content stays on calm, highly legible surfaces.

**Where glass is used:** tab bar (floating), screen headers/top bars as content scrolls beneath them, bottom sheets, dialogs, toasts, menus/popovers, segmented controls and filter bars, the live-scoring control dock that holds the scoring keys and secondary actions, floating action buttons, and the live score header band. **Where it is not:** tables (scorecards, standings), long lists, form fields, and any text-dense content — those sit on solid or near-solid surfaces so numbers stay readable outdoors (§72).

**Light mode:** base is a pale, translucent white or very light neutral tint; edges get near-white rim highlights (white at low opacity) like light catching a glass edge; text and icons on glass are high-contrast dark charcoal or black. It must blend into bright backgrounds without harsh blocks.

**Dark mode:** base is a deep, desaturated tint (charcoal with a hint of navy, teal or violet — never transparent black); rim highlights are subtle and coloured (soft teal, faint blue or muted violet), never bright white glare; text and icons are bright white or pale pastel. Frosted blur with a slight tint must stand out clearly and never look muddy.

**Platforms:** iOS 26+ uses the native Liquid Glass material (`expo-glass-effect` `GlassView`, gated by `isLiquidGlassAvailable()`); other iOS versions, Android and web use a frosted blur (`expo-blur`) plus the tint, rim highlight and a soft specular sheen so the material reads the same everywhere. Glass needs something behind it to read as glass: content scrolls beneath glass chrome, and backgrounds may carry a very subtle ambient wash (no loud gradients, no stock imagery — §101 still applies).

**Legibility and accessibility are non-negotiable:** text on glass meets WCAG AA (4.5:1, 3:1 for large score figures) against the worst-case content behind it, achieved through tint opacity; the system "Reduce Transparency" preference and an in-app **Reduce transparency** setting replace every glass surface with an opaque surface of the same tint; high-contrast needs and §78 still apply; motion of glass (morphing, interactive highlights) honours reduced motion. Scoring keys keep solid, high-contrast faces — the glass is the dock around them, not the key faces.

**Light theme (designed separately, not an inversion):** a cool ice / frosted environment — background `#F0F5F8` with faint cyan ambient light, white translucent glass with near-white rims and a faint cyan edge, deep teal ink for text, and teal/cyan for interaction. Because cyan on white fails WCAG, light-mode text, icons and interactive fills use deep teals that pass AA (≥4.5:1 text, ≥3:1 UI components); bright cyan appears only in non-essential glows, rims and highlights.

**Hierarchy (unchanged from §106):** solid content → glass controls. Solid: page background, large content areas, tables, data-heavy sections, charts, score content. Glass: bottom and top navigation, the floating scoring dock (the **strongest** glass element — it floats above the match), floating action buttons, menus, bottom sheets, player detail sheets, match action controls.

**Still binding:** §72 outdoor contrast, §78 colour-independent information (wicket = icon + text, not only red), §73 live-scoring hierarchy and the eight primary keys `0 1 2 3 4 6 EXTRAS WICKET`, §49 dashboard without a card per statistic.
