# Tournament Rules Engine Design

Engineering design for the §60 "TournamentRulesEngine": structure generation and guards in `src/domain/tournament/{rng,pools,fixtures,knockout,slots,defaults,templates,stateMachine}.ts` (owner WP-tournament-structure) and the orchestration in `evaluate.ts` / `impact.ts` (owner WP-tournament-standings). Standings, NRR and qualification have their own documents: [STANDINGS_CALCULATOR.md](STANDINGS_CALCULATOR.md), [NRR_CALCULATOR.md](NRR_CALCULATOR.md), [QUALIFICATION_ENGINE.md](QUALIFICATION_ENGINE.md). ## 1. Principles

* **Pure and seeded.** No `Math.random`, no clock. Every random result carries the seed that produced it (`PoolAssignment.seed`, `FixturePlan.seed`, `StageConfig.seedingSeed`, audit entry), so a draw can be replayed, explained and undone (§31).
* **Generate → preview → confirm.** Generators return drafts (`PoolAssignment`, `FixtureDraft[]`, `KnockoutBracketPlan`); services persist them only on confirmation (§36). Ids are pre-assigned by the injected `IdGenerator`, in call order, so the same inputs produce the same drafts.
* **Members are sides.** Pools, fixtures and tables work on `FixtureSide` (a team or a slot), so later stages (Super 8, semifinals) are built before their teams are known (§45).
* **Rules are data** (§97). Nothing here knows "top 2" or "2 points for a win"; those are `QualificationRule`s, `PointsSystem`s and `KnockoutConfig`s.
* **Scale.** Everything is O(n²) at worst in teams (round robin); 128 teams / 16 pools / ~500 fixtures stay far below the 100 ms evaluation budget.

## 2. Seeded PRNG (`rng.ts`)

### 2.1 mulberry32

State: one uint32 `a`. Each call:

```
a ← (a + 0x6D2B79F5) mod 2³²
t ← a
t ← imul(t xor (t >>> 15), t or 1)
t ← t xor (t + imul(t xor (t >>> 7), t or 61))
return ((t xor (t >>> 14)) >>> 0) / 2³²                  uniform in [0, 1)
```

`imul` is 32-bit multiplication (`Math.imul`); only 32-bit integer operations are used, so Hermes, V8 and JavaScriptCore produce identical sequences.

Golden values (assert in `rng.test.ts`):

| Seed | 1st | 2nd | 3rd |
|---|---|---|---|
| 1 | 0.6270739406 | 0.0027357212 | 0.5274470400 |
| 847291 | 0.4183025225 | 0.6612153111 | 0.4243005631 |

### 2.2 Helpers

* `normalizeSeed(input)`: an integer number or a string of digits → value mod 2³² (`"847291"` → 847291; negative numbers wrap: `((n mod 2³²) + 2³²) mod 2³²`); any other text → FNV-1a 32-bit over the trimmed string's UTF-16 code units (`h ← 2166136261; for c: h ← imul(h xor c, 16777619) >>> 0`). `normalizeSeed("Spring Cup 2026") = 520673282`.
* `randomInt(rng, max) = ⌊rng() × max⌋`.
* `shuffle(items, rng)`: Fisher–Yates from the end on a copy: for `i = n−1 … 1`: `j = randomInt(rng, i + 1)`, swap `i, j`.
* Fresh seeds for "Random" are generated by the **service** (`expo-crypto` `getRandomValues(new Uint32Array(1))[0]`) and shown to the organizer before anything is saved.

## 3. Pools (`pools.ts`)

### 3.1 Sizes and naming

`distributePoolSizes(n, p)`: `base = ⌊n/p⌋`, `rem = n mod p`; the first `rem` pools get `base + 1`. (10, 3) → [4, 3, 3]; (16, 4) → [4, 4, 4, 4]; (13, 4) → [4, 3, 3, 3]. Explicit uneven sizes (§32) are accepted when they sum to n. `poolName(i)`: bijective base-26 — "Pool A" … "Pool Z", "Pool AA", "Pool AB".

### 3.2 Assignment methods

| Method | Algorithm | Example |
|---|---|---|
| `assignRandom(members, spec, poolIds, seed)` | `shuffle(members, mulberry32(seed))`, then fill pools in order up to their sizes | 16 teams T01…T16, seed 847291 → A: T02 T12 T08 T04 · B: T09 T01 T11 T03 · C: T14 T15 T16 T05 · D: T13 T06 T10 T07 (golden test) |
| `assignSeeded(teams, poolIds)` | order by seed ascending (unseeded last, then by name), deal A, B, …, P, P, …, B, A, A, B … (snake) | 8 seeded teams, 2 pools → A: 1 4 5 8 · B: 2 3 6 7; 16 teams, 4 pools → A: 1 8 9 16 · B: 2 7 10 15 · C: 3 6 11 14 · D: 4 5 12 13 |
| `assignSlotsToPools(slots, poolIds, {kind: 'snake'})` | slots by index, snake deal | top 2 of Pools A–D (A1 B1 C1 D1 A2 B2 C2 D2) into 2 groups → Group 1: A1 D1 A2 D2 · Group 2: B1 C1 B2 C2 (see note) |
| `assignSlotsToPools(…, {kind: 'fixed_order', slotIndexesPerPool})` | exactly the given indexes per pool | Super 8 from top 2 of Pools A–D (slot indexes A1=0, B1=1, C1=2, D1=3, A2=4, B2=5, C2=6, D2=7) with `[[0,5,2,7],[1,4,3,6]]` → Group 1: A1 B2 C1 D2 · Group 2: B1 A2 D1 C2 |

Note on `snake` for slots: dealing A1, B1, C1, D1, A2, B2, C2, D2 into **two** groups snake-wise gives Group 1 = A1, D1, A2, D2 — both Pool A qualifiers meet again. Snake is only safe when the number of target pools equals the number of source pools (4 → 4) or the source positions are already interleaved; the Super 8 template therefore uses `fixed_order`, and the pools step shows a warning when a snake deal places two slots with the same source pool together ("A1 and A2 are in the same group").

### 3.3 Transfers (§33)

Pure functions on a `PoolAssignment`; members compared by value (`team` by teamId, `slot` by slotId):

* `moveMember(a, m, to)`: remove `m` from its pool, append to `to`.
* `swapMembers(a, x, y)`: exchange positions (within or across pools).
* `replaceMember(a, out, in)`: `in` must not be assigned anywhere; takes `out`'s position.

Every other member keeps its pool and order (tested). Transfers after fixtures exist are **not** done with these functions directly but through `ProposedChange` (`pool_move`, `pool_swap`, `team_replace`, `pools_replace`) so the impact preview runs (§10).

### 3.4 Warnings

`poolWarnings(assignment, entrants)`: `UNEVEN_POOLS` (sizes differ: "Teams in different pools may play different numbers of matches."), `EMPTY_POOL`, `SINGLE_TEAM_POOL` (no fixtures possible), `TEAM_IN_MULTIPLE_POOLS`, `UNASSIGNED_TEAMS` against the stage's entrants (`stageEntrants`: its entry slots incl. direct entries, or — for a stage without entry rules — the active teams not directly entered elsewhere). A team with a `direct_entry` into the semifinals is therefore never "unassigned" in the group stage.

## 4. Round robin (`fixtures.ts#roundRobin`)

### 4.1 Circle method with a bye marker

```
list ← entrants (input order)
if n is odd: list ← [BYE] + list                         the bye marker takes the fixed position
m ← |list|                                                 even
for r in 0 … m−2:
  for i in 0 … m/2 − 1:
    x ← list[i], y ← list[m−1−i]
    if x or y is BYE: bye ← the other; continue
    i = 0: sides ← (r even) ? (x, y) : (y, x)             alternate the fixed entrant
    i odd: sides ← (y, x)
    i even (≥ 2): sides ← (x, y)
  list ← [list[0], list[m−1], list[1], …, list[m−2]]       rotate all but position 0
```

Properties (tested for n = 2…17 and 128): every pair meets exactly once per leg; `n − 1` rounds for even n, `n` rounds with exactly one bye each for odd n; no side twice in a round; each entrant is side A ⌊(n−1)/2⌋ or ⌈(n−1)/2⌉ times per leg. For even n entrant 0 is the fixed element; for odd n the bye marker is fixed, so the bye rotates through every entrant.

Examples (entrants A, B, C, … in input order):

| n | Rounds |
|---|---|
| 4 | R1 A v D, C v B · R2 C v A, B v D · R3 A v B, D v C |
| 5 | R1 D v A, B v C (bye E) · R2 C v E, A v B (bye D) · R3 B v D, E v A (bye C) · R4 A v C, D v E (bye B) · R5 E v B, C v D (bye A) |
| 6 | R1 A v F, E v B, C v D · R2 E v A, D v F, B v C · R3 A v D, C v E, F v B · R4 C v A, B v D, E v F · R5 A v B, F v C, D v E |

### 4.2 Legs and drafts

* `legs = k`: leg 1 as above; leg 2 = leg 1 with sides swapped; leg 3 = leg 1 again; … Round numbers continue across legs (a 4-team double round robin has rounds 1–6).
* Per-pool legs: `Pool.legs ?? stage.config.fixtureGeneration.legs` (with uneven 4/3/3 pools the organizer may give the 3-team pools a double round robin — 4 matches per team against 3 in the 4-team pool — or keep single legs and choose a normalisation, §32).
* `draftsFromRoundRobin(rounds, defaults, ids)`: drafts in round order, `matchNumber` from `defaults.startMatchNumber` (continuing the tournament's numbering), `status: scheduled`, `round`, `leg`, `bracket: null`, `isFinal: false`, format/rules/venue from defaults.
* Fixture count per pool = `legs × n(n−1)/2`: 4 teams single RR = 6; the §92 tournament (2 × 4) = 12 group fixtures + 2 SF + 1 final = 15.

### 4.3 Validation and scheduling

`validateFixtureDrafts(drafts, ctx)`:

| Code | Severity | Rule |
|---|---|---|
| `SAME_SIDE_TWICE` | error | side A = side B |
| `SIDE_NOT_IN_POOL` | error | pool fixture with a side not in `poolMembers[poolId]` |
| `SIDE_NOT_IN_TOURNAMENT` | error | side not in `tournamentSides` |
| `DUPLICATE_ENCOUNTER` | warning | a pair meets more than `legsByPool.get(pool) ?? defaultLegs` times |
| `TEAM_DOUBLE_BOOKED` | warning | a side has two fixtures at the same date + time |
| `OUTSIDE_TOURNAMENT_DATES` | warning | date before `startDate` or after `endDate` |

`scheduleSequential(drafts, {startDate, matchesPerDay, times, restDates})`: walk drafts in round order; place each on the current date at `times[k mod |times|]` while the date has < `matchesPerDay` fixtures and neither side already plays that date; otherwise try the next date (skipping `restDates`); dates are advanced by pure `YYYY-MM-DD` arithmetic (days-in-month table, leap years). Deterministic; never double-books a side on one day.

### 4.4 Pool move prefill (`fixturesForPoolMove`)

Moving Lions from Pool A {Tigers, Lions, Eagles, Hawks} to Pool C {Kings, Royals, Titans} after Lions v Tigers was played (single RR, next match number 25):

* `removeFixtureIds` = Lions v Eagles, Lions v Hawks (Pool A fixtures of Lions without a match);
* `addFixtures` = Match 25 Lions v Kings, 26 Royals v Lions, 27 Lions v Titans (sides alternate per pairing and leg);
* Lions v Tigers stays in Pool A with its frozen teams. Because a result counts in a table only when both teams are members of it, that result leaves Pool A's table (Tigers lose its points) and does not enter Pool C's; the impact preview states it ("Tigers lose 2 points in Pool A: their win over Lions no longer counts").

## 5. Knockout brackets (`fixtures.ts#knockoutBracket`, `knockout.ts`)

### 5.1 Geometry

* `P` = next power of two ≥ n; `totalRounds = log₂P`; byes = `P − n`, given to the top seeds.
* `standardBracketOrder(P)`: `order(2) = [1, 2]`; `order(2k) = flatMap(s ∈ order(k)) → [s, 2k + 1 − s]`. → 4: [1, 4, 2, 3]; 8: [1, 8, 4, 5, 2, 7, 3, 6]; 16: [1, 16, 8, 9, 4, 13, 5, 12, 2, 15, 7, 10, 3, 14, 6, 11].
* Round 1, position i pairs seeds `order[2i]` v `order[2i+1]`; a seed > n is a bye (no fixture at that position — positions keep their bracket index, so gaps are allowed).
* Round r ≥ 2, position p takes the winners of round r−1 positions 2p and 2p+1: a real fixture → a progression slot `bracket_winner(stage, r−1, pos)`; a bye → the bye entrant's side directly.
* `rounds` (from `KnockoutConfig.rounds`) stops after that many rounds (a QF-only stage); otherwise the single main fixture of the last round is the final (`isFinal: true`).
* `thirdPlacePlayoff` (only when the bracket reaches a final with ≥ 4 entrants): `third_place` fixture, round = final round, position 0, sides `bracket_loser` of both semifinals.
* `bracketShape(n, rounds)` returns `{size: P, totalRounds, roundsPlayed, winners: P / 2^roundsPlayed}` — used to expand `knockout_winners` before any fixture exists.

### 5.2 Names and labels

`roundName(teamsInRound)`: 2 → Final, 4 → Semifinal, 8 → Quarterfinal, 16 → Round of 16, 32 → Round of 32, else "Round k"; teams in round r = `P / 2^(r−1)`. Fixture labels ("QF1", "SF2") number the round's **existing** main fixtures by position order, so a bracket with byes shows QF1, QF2 rather than QF2, QF4. `defaultSlotLabel` uses the same numbering ("Winner SF1", "Loser SF2").

### 5.3 Example: 6 entrants

Seeds 1–6, P = 8, byes to seeds 1 and 2, order [1, 8, 4, 5, 2, 7, 3, 6]:

| Round | Pos | Fixture | Sides |
|---|---|---|---|
| 1 (Quarterfinal) | 0 | — (bye) | seed 1 advances |
| 1 | 1 | QF1 | seed 4 v seed 5 |
| 1 | 2 | — (bye) | seed 2 advances |
| 1 | 3 | QF2 | seed 3 v seed 6 |
| 2 (Semifinal) | 0 | SF1 | seed 1 v Winner QF1 |
| 2 | 1 | SF2 | seed 2 v Winner QF2 |
| 3 (Final) | 0 | Final (`isFinal`) | Winner SF1 v Winner SF2 |
| 3 | 0 (`third_place`) | Third place | Loser SF1 v Loser SF2 (if enabled) |

Progression slots, indexed from `firstSlotIndex` (= highest entry index + 1): Winner QF1, Winner QF2, Winner SF1, Winner SF2 (+ Loser SF1, Loser SF2). Their sources name `(stage, round, position)`, never fixture ids, so a re-draw (`fixtures_replace`) that regenerates fixture ids leaves them valid. `entrySlotSeeds` records the seed of each entry-slot entrant (→ `StageSlot.seed`, used by `higher_seed`); `byes` = [seed 1, seed 2].

### 5.4 The §92 bracket

8-team T20 template: entry slots A1 (0), B1 (1), A2 (2), B2 (3), seeding `fixed` → seed order A1, B1, A2, B2 → P = 4, order [1, 4, 2, 3]: SF1 = A1 v B2, SF2 = B1 v A2; progression slots Winner SF1 (4), Winner SF2 (5); Final = Winner SF1 v Winner SF2, `isFinal`, stage `decidesChampion`.

## 6. Seeding (`knockout.ts#seedEntrants`)

Every method produces a **seed order**; the bracket always pairs by standard order (§5.1).

### 6.1 `fixed`

1. **Paired pools** (every source pool contributes exactly two entrants and the pool count is even): couple pools (A,B), (C,D), …; the desired first-round matches in bracket-position order are, for the top half, `X1 v Y2` of each couple and, for the bottom half, `Y1 v X2` of each couple. Seeds are then assigned by inverting the standard order: for position i with desired match (u, v), seed `order[2i]` ← u and seed `order[2i+1]` ← v.
   * 2 pools: A1 v B2 (top), B1 v A2 (bottom) → seed order A1, B1, A2, B2.
   * 4 pools: A1 v B2, C1 v D2 (top), B1 v A2, D1 v C2 (bottom) → with order [1,8,4,5,2,7,3,6]: seeds 1 A1, 8 B2, 4 C1, 5 D2, 2 B1, 7 A2, 3 D1, 6 C2 → seed order **A1, B1, D1, C1, D2, C2, A2, B2**. Each pool's winner and runner-up are in opposite halves.
2. **Otherwise**: pool-positioned entrants by (position asc, pool index asc), then entrants without a pool position (best-of, overall, manual, direct entry) by slot index. A repair pass then walks round-1 pairs in position order; if both sides come from the same pool, it swaps the second side with the second side of the next pair (wrapping) when that makes both pairs cross-pool; if no swap works the pairing stays and the preview shows "Two Pool C teams meet in the first round". Example 3 pools × 2: A1, B1, C1, A2, B2, C2 → pairs (A1 bye), (A2 v B2), (B1 bye), (C1 v C2) → repaired to (A2 v C2), (C1 v B2).

### 6.2 `random`

`shuffle(entrants, mulberry32(seed))`; the seed is required, stored in `StageConfig.seedingSeed` and shown ("Draw seed 58213").

### 6.3 `ranking`

By `rank` ascending (1 v N, 2 v N−1 …). Rank = the entrant's record in its source stage, compared across pools with `StageConfig.seedingNormalization` (the same comparison-table machinery as `best_of_position`, see QUALIFICATION_ENGINE §4), or the pre-tournament seed for a first-stage knockout. `knockoutGenerationGuard('ranking', entrySlots)` refuses while any entry slot is not `final`: "Seeding by ranking is possible once all 8 qualifiers are known." `fixed` and `random` may be generated from unresolved slots.

## 7. Knockout advancement (`knockout.ts#knockoutAdvancer`)

Input: the fixture, its teams (frozen `matchSides` once it has a match), the current match's summary, the stage's `KnockoutConfig` (else `DEFAULT_KNOCKOUT_CONFIG`), and `seedOf`.

| Current match | Config | Winner | Basis |
|---|---|---|---|
| none / not terminal | — | null | `not_played` |
| win, walkover, awarded with winner | — | that team | `result` / `walkover` / `awarded` |
| tie with decider (super over, boundary count, bowl-out, coin toss, organizer) | — | decider winner | `tie_decider` |
| undecided tie | `tiedMatch: higher_seed` | better (lower) `seedOf`; unknown or equal seeds → null | `higher_seed` / `organizer_required` |
| undecided tie | `super_over` (super over(s) still tied), `boundary_count` (still level), `organizer` | null | `organizer_required` |
| no result, abandoned, awarded without winner | `noResult: higher_seed` | better seed | `higher_seed` |
| same | `shared` | null (both teams share) | `shared` |
| same | `replay`, `organizer` | null | `organizer_required` |

`seedOf(team)` = `StageSlot.seed` of the entry slot the team occupies in this stage, else its pre-tournament `TournamentTeam.seed`, else null. `loserTeamId` is the other team when a winner exists. A `slot_assignment` override on the receiving slot beats the advancer (applied in `resolveStageSlots`). `startFixtureMatch` forces `rules.superOver.enabled = true` when `tiedMatch = super_over`, so a knockout tie normally resolves on the field.

## 8. Slots (`slots.ts`)

### 8.1 Expansion

`expandEntryRules(targetStageId, rules, sources, existing, ids)` turns the target stage's entry rules into ordered entry slots (`role: 'entry'`, `seed: null`), indexes contiguous from 0 in rule order:

| Rule | Slots (labels) |
|---|---|
| `top_per_pool {count 2, fromPosition 1}` over A, B | A1, B1, A2, B2 (by position, then pool order) |
| `top_per_pool {count 2, fromPosition 3}` | A3, B3, A4, B4 |
| `pool_position {poolId A, position 1}` | A1 |
| `best_of_position {position 2, count 4}` | Best runner-up, 2nd best runner-up, 3rd…, 4th… (`best_of_position` sources rank 1..4) |
| `top_overall {count 8}` | 1st overall … 8th overall |
| `knockout_winners {source QF stage}` | Winner QF1 … one `bracket_winner` per main position of the source's last played round (from `bracketShape`, no fixtures needed) |
| `manual {count 4}` | TBD 1 … TBD 4 (`manual`, team null) |
| `direct_entry {teamIds}` | the team names (`manual` with the team set) |

**Re-expansion** (source pools changed, bracket re-drawn, rules edited) passes the stage's current slots as `existing`: slot i keeps `existing[i].id`, so pool entries, fixture sides and overrides that reference it stay valid; surplus slots are returned in `removed` and the plan deletes them (their unplayed fixture references are rewritten or removed; overrides keep their payload, the FK column is nulled).

### 8.2 Entrants and resolution

* `stageEntrants(snapshot, stageId)` = the stage's entry slots as `slot` sides; for a stage with no entry rules, the active teams not directly entered into another stage.
* Slot → team resolution (`qualification.ts#resolveStageSlots`) is specified in [QUALIFICATION_ENGINE.md §3](QUALIFICATION_ENGINE.md#3-slot-resolution).
* **Frozen sides.** A fixture with a match never re-resolves its sides: `resolveFixtureTeams` returns `fixture.matchSides` (`frozen: true`). Slots are resolved only for fixtures without a match; a later change of who occupies "A1" appears as a `SlotChange` with `playedFixtureIds` and never rewrites a played semifinal.

## 9. Evaluation pipeline (`evaluate.ts#evaluateTournament`)

```
stages ← snapshot.stages sorted by orderIndex          every slot source has a lower orderIndex
earlier ← []
for stage in stages:
  slots      ← resolveStageSlots(snapshot, stage, earlier)
  members    ← pool entries mapped through slots (+ kept predecessors of replaced / withdrawn teams)
  tables     ← computeStandings per pool; overall + comparisonTables for every downstream best_of / overall source
  ties       ← level groups straddling a downstream slot boundary in a complete table → unresolvedTies
  qual       ← computeQualification(snapshot, stage, tables, earlier)
  progress   ← terminal or cancelled fixtures / all fixtures of the stage
  earlier.push(StageEvaluation)
champion       ← resolveChampion(snapshot, earlier)      stage with decidesChampion only
currentStageId ← first stage not complete, else the last stage
```

Services memoise `evaluateTournament` by `snapshot.version` (one cached evaluation per open tournament); what-if and impact evaluate copies and never touch the cache. Budget: 128 teams / 16 pools / ~500 fixtures < 100 ms without enumeration.

## 10. Structural changes (`impact.ts#planChange`)

One interpretation of every change (D13): `planChange(snapshot, change, ctx)` → `ChangePlan`; the preview evaluates `applyPlan(snapshot, plan)`; the service persists the same plan when the snapshot version is unchanged (`CONFLICT` otherwise).

| Change | Plan rows | Played data |
|---|---|---|
| `pool_move` | move the pool entry; delete `removeFixtureIds`; insert `addFixtures` | played fixtures keep teams and pool |
| `pool_swap` | exchange entries; rewrite each member into the other's UNPLAYED fixtures in those pools | kept |
| `team_replace` | Y takes X's entries and unplayed fixtures; X `replaced` (`replacedByTeamId`); `priorResults`: transfer → Y.`inheritsFromTeamId` = X; keep → nothing else; expunge → `expunge_results` override | per policy |
| `team_withdraw` | X `withdrawn`; remaining fixtures → `matchesToCreate` with `match_ended { walkover }` for the opponent, or `cancelled`; optional `expunge_results` | kept unless expunged |
| `pools_replace` | replace entries of the stage; store `seed` in `seedingSeed` | fixtures with matches kept |
| `team_seeds_change` | tournament-team seeds | — |
| `stage_upsert` / `stage_delete` | stage, pools, slots (only stages without started matches) + re-expansion of every dependent stage | — |
| `fixture_add` / `fixture_update` / `fixture_delete`, `fixtures_replace` | fixture rows; `fixtures_replace` swaps fixtures without a match, upserts progression slots, stores the draw seed, re-expands dependants | fixtures with matches kept |
| `rules_change` | tournament rules or the stage's config | all results re-scored |
| `slot_change` | slot source | played fixtures keep frozen teams |
| `override_apply` / `override_revoke` | override rows | — |
| `match_result_change` | `summaryChanges` only (preview) | MatchService writes the match |

`computeImpact` diffs the two evaluations and inspects fixtures (severity `destructive` when started/completed match data would be detached, removed or re-attributed; `warning` for standings/NRR/qualification/slot changes; `info` for scheduling; `none` otherwise) and sets `blocked` from `tournamentEditPolicy`.

## 11. Templates (`templates.ts`)

| Id | Structure | Champion stage |
|---|---|---|
| `builtin:8-team-t20` | Groups: 2 pools × 4, single RR · Knockouts: entry `top_per_pool 2` (A1, B1, A2, B2 = slots 0–3), `fixed`, SF + Final (progression slots 4–5) | Knockouts |
| `builtin:4-team-league` | one league, double RR | League (top of table) |
| `builtin:8-team-knockout` | one knockout stage, 8 entrants, `ranking` by pre-tournament seed | Knockout |
| `builtin:16-team-groups` | 4 pools × 4 single RR · knockout QF, SF, Final from top 2, `fixed` | Knockout |
| `builtin:20-team-pools` | 4 pools × 5 single RR · pool winners → SF, Final, `fixed` | Knockout |

`instantiateTemplate` creates stages (fresh ids, `orderIndex` = template order), pools via `poolName`, entry slots via `expandEntryRules` (`knockout_winners` from `bracketShape`), and slot pool entries from `poolSlotIndexes`. `templateFromSnapshot` inverts it (slot-built pools → `poolSlotIndexes`, knockout progression / `bracket_winner` entries → `knockout_winners`, direct entries → `direct_entry {count}`) and must round-trip. `templateFitsTeamCount` → "Designed for 8 teams; you have 10."

## 12. State machine guards (`stateMachine.ts`)

All guards return `Guard` (`{ok: true, warnings}` or `{ok: false, reason}` with an organizer sentence).

### 12.1 Tournament (`canTransitionTournament`)

| From → to | Guard (ctx: `TournamentGuardContext`) | Refusal text |
|---|---|---|
| draft → registration | always (info saved by the caller) | — |
| registration → structure_configured | `activeTeamCount ≥ 2 ∧ stageCount ≥ 1` | "Add at least two teams and one stage." |
| structure_configured → pools_configured | `poolsComplete` (vacuously true for knockout-only structures once seeding is chosen) | "3 teams are not in a pool yet." |
| pools_configured → fixtures_generated | `firstStageFixturesConfirmed` | "Confirm the first stage's fixtures." |
| fixtures_generated → active | always (first match started, or organizer starts) | — |
| active → completed | `championDecided ∨ allStagesComplete` | "The champion hasn't been decided yet." |
| completed → archived, archived → completed | always | — |
| completed → active | always (audited reopen) | — |
| structure_configured → registration, pools_configured → structure_configured, fixtures_generated → pools_configured | `matchesStarted = 0` | "Matches have already started." |
| anything else | refused | "A tournament can't go from Active back to Draft." |

Warnings (`ok: true`): e.g. `fixtures_generated → active` with fixtures of later stages still unresolved ("Semifinal teams will be filled in as results come in.").

### 12.2 Edit policy (`tournamentEditPolicy`)

The function first classifies the situation, then returns the STATE_MACHINES.md §3 row:

```
archived                                         → row "archived"
completed                                        → row "completed"
setup states (draft … pools_configured)          → row "setup"
fixtures_generated, or active with matchesStarted = 0 → row "fixtures_generated (no match started)"
active, matchesStarted > 0, matchesCompleted = 0 → row "matches started, none completed"
active, matchesCompleted > 0                     → row "completed matches exist"
seeds         = the row's Rules column
deleteTournament = archived ? forbidden : matchesStarted = 0 ? allowed : confirm
```

The UI maps `allowed` → apply, `warn` → ImpactSheet one tap, `confirm` → ImpactSheet + reason, `forbidden` → explanation of what to do instead ("Unarchive the tournament first.").

### 12.3 Stage, fixture, match

* `canTransitionStage`: pending → active requires `fixturesConfirmed` (called when the stage's first match starts; `entrantsResolved = false` is a warning, not a refusal: "2 semifinal places are still to be decided."); active → completed requires `allFixturesTerminal`; completed → active always (a result was corrected or a match reopened).
* `canTransitionFixture`: exactly the STATE_MACHINES.md §5 edges; `abandoned → rescheduled` requires `replayAllowed` (`StageConfig.abandonedMatches = 'replay'`, or `KnockoutConfig.noResult = 'replay'` in knockout stages); `→ live | completed | abandoned` are mirror transitions reachable only through MatchService (`FixturePatch.status` cannot name them).
* `canTransitionMatch`: STATE_MACHINES.md §1 edges; `scheduled | postponed → completed` only with `hasDeliveries = false` (walkover / award without play).
* `matchEditPolicy(status, {inTournament})`: STATE_MACHINES.md §1 table (history: live → `warn`, completed → `confirm`; delete: standalone `confirm`, tournament `forbidden`).
